# M5 管线设计调研报告

> **调研日期**: 2026-05-11  
> **调研方法**: 源代码全量审查 + 架构文档分析 + 数据流追踪  
> **评审结论**: 三管线划分**方向正确，但需调整边界**

---

## 一、你提出的三管线划分

| 管线 | 你的定义（推测） | 对应当前代码 |
|:---|:---|:---|
| Agent 管线 | Agent 推理/调度/协作的链路 | `graph.py` → `swarm_coordinator.py` → `task_board.py` → Workers |
| Tools 管线 | 工具注册/发现/执行 | `tools.py` → `tool_search.py` → `skill_loader.py` → 各工具实现 |
| 数据管线 | PDF 入库/检索/存储 | `pdf_parser.py` → `es_indexer.py` → `semantic_search.py` → `graph_search.py` |

---

## 二、我的评估：方向正确，但有三个问题

### ✅ 正确之处

1. **关注点分离清晰** — 把"思考者"(Agent)、"手脚"(Tools)、"食物"(Data) 三个维度拆开，符合经典的 Agent 架构分层。
2. **对标行业实践** — 类似 LangChain 的 Agent / Tool / Retriever 三层，也类似 RAGFlow 的 Pipeline / Chunk / Search 分法。
3. **与 M1~M4 里程碑衔接** — 之前已经分阶段搭好了地基，现在用管线思维重新审视全局是很好的时机。

### ⚠️ 问题 1：Agent 管线和 Tools 管线的边界模糊

看当前代码的**实际依赖关系**：

```
graph.py (Agent)
  ├── 直接 import tools.py 的 ALL_TOOLS      ← Agent 硬依赖 Tools
  ├── 直接 import skill_loader.py             ← 又是 Tools 的一部分
  └── skill_loader.py
        └── 直接 import tools.py 的 get_tools_for_step  ← 循环依赖风险
```

问题在于：**当前 `skill_loader.py` 既属于 Agent 管线（它决定给 Agent 哪些工具），又属于 Tools 管线（它操作工具注册表）**。如果你把它拆成两条独立管线，这个文件放哪边？

### ⚠️ 问题 2：数据管线缺少"出口"定义

当前数据管线实际上是**两条断裂的子管线**：

```
入库管线（Ingestion）:   PDF → Marker解析 → 分块 → ES索引 → Neo4j三元组
                          ↑ 由 upload_routes.py 触发

检索管线（Retrieval）:   用户Query → Embedding → BM25+向量+RRF → 结构化结果
                          ↑ 由 tools.py/search_metallurgy_text 触发
```

它们之间只通过 **ES 索引** 间接连接，没有统一的管线接口。把它们笼统叫做"数据管线"会掩盖这个设计缺陷。

### ⚠️ 问题 3：缺少"交互管线"

当前代码中有一条被忽略的隐含管线：

```
交互管线（Interaction）:
  用户输入 → chat_routes.py → ChatWorker → (记忆预加载 + 安全阀门 + LLM调用)
                                            → Redis PubSub → SSE → 前端渲染
```

这条管线跨越了 Agent、Tools、Data 三个层面，但本质上是一条**独立的交互链路**。ChatWorker 不走 `graph.py`，它是直接对接 LLM 的"快通道"。如果不把它纳入管线视野，M5 升级时可能会漏掉它。

## 三、改进建议：四管线模型

建议将三管线调整为 **四管线**，让边界更清晰：

```
┌─────────────────────────────────────────────────────────────────┐
│                    M5 四管线架构                                  │
│                                                                  │
│  ┌──────────────┐                                               │
│  │  ① 数据入库    │  PDF → 解析 → 分块 → 向量化 → ES/Neo4j写入   │
│  │  (Ingestion)  │  触发点: upload API                           │
│  └──────┬───────┘                                               │
│         │ 数据沉淀到 ES + Neo4j + PostgreSQL                      │
│         ▼                                                        │
│  ┌──────────────┐                                               │
│  │  ② 工具与检索  │  工具注册 → 渐进披露 → 检索执行 → 结果格式化  │
│  │  (Tooling)    │  含: 文本检索 / 图谱查询 / 沙盒 / VLM         │
│  └──────┬───────┘                                               │
│         │ 提供原子能力给上层                                       │
│         ▼                                                        │
│  ┌──────────────┐                                               │
│  │  ③ Agent 推理  │  Coordinator → 规划 → Worker ReAct 循环      │
│  │  (Reasoning)  │  含: 任务拆解 / 黑板 / 评估 / 结果聚合         │
│  └──────┬───────┘                                               │
│         │ Agent 推理结果                                          │
│         ▼                                                        │
│  ┌──────────────┐                                               │
│  │  ④ 交互与呈现  │  对话管理 → 记忆 → SSE推送 → 前端渲染        │
│  │  (Delivery)   │  含: ChatWorker / AskUser / 记忆持久化         │
│  └──────────────┘                                               │
└─────────────────────────────────────────────────────────────────┘
```

### 对比表

| 维度 | 你的三管线 | 建议四管线 | 区别 |
|:---|:---|:---|:---|
| 数据入库 | 数据管线 | ① Ingestion（入库管线） | 拆出入库，不和检索混为一体 |
| 检索执行 | 数据管线 | ② Tooling（工具管线） | 检索是"工具的一种"，归入工具层 |
| 工具注册 | Tools管线 | ② Tooling（工具管线） | 合并 |
| Agent 推理 | Agent管线 | ③ Reasoning（推理管线） | 名称更精确 |
| 对话/SSE/记忆 | *未覆盖* | ④ Delivery（交互管线） | **新增**，覆盖 ChatWorker + 前端 |

## 四、各管线 M5 升级方向

### ① 入库管线 (Ingestion) — 当前完成度 70%

**M5 应补齐**：
- 管线状态追踪（入库进度 SSE 推送）
- 增量索引（重复 PDF 检测）
- 批量入库 CLI 脚本

### ② 工具管线 (Tooling) — 当前完成度 85%

**M5 应补齐**：
- 沙盒安全加固（CPU/内存/时间限制）
- 工具执行监控 & 日志审计
- 新增 PyCalphad 热力学工具

### ③ 推理管线 (Reasoning) — 当前完成度 60%

**M5 应补齐**：
- Coordinator 与 ChatWorker 统一（当前两条路径割裂）
- Worker ReAct 循环中间步骤 SSE 进度透传
- Worker 错误恢复 & 重试机制

### ④ 交互管线 (Delivery) — 当前完成度 75%

**M5 应补齐**：
- 多用户会话隔离（当前硬编码 default_session）
- 对话历史持久化到 PostgreSQL（当前仅 Redis，重启丢失）
- 知识图谱前端可视化

## 五、建议实施顺序

1. **Week 1**: ① 入库管线加固（状态追踪、增量检测）
2. **Week 2**: ② 工具管线安全（沙盒限制、执行监控）
3. **Week 3**: ③ 推理管线统一（Coordinator-ChatWorker 打通、SSE 进度透传）
4. **Week 4**: ④ 交互管线升级（多用户隔离、会话持久化、图谱可视化）
